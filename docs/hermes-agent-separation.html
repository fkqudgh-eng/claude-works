Hermes · Agent Architecture · rev 0.1

모놀리식 헤르메스를
세 개의 협력 에이전트로 분리한다

지금의 헤르메스는 “판단·계획·구현·검증”을 한 몸으로 처리한다. 이를 orch(오케스트레이션) · spec(태스크 생성) · impl(구현) 로 나누고, 그 위에 GOAL_LOOP(exec → test → verify → eval → 새 버전) 자기개선 루프를 얹는다. 작은 단위에서 큰 단위로 쌓아 올린다.

orch 제어평면 spec 태스크·검증정의 impl 구현·셀프테스트 근거: menu v1→v4 · userscript self-test
01  Relationship Map

에이전트 관계도 — orch 를 유일한 라우터로 두는 스타 토폴로지

spec 과 impl 은 서로 직접 대화하지 않는다. 모든 태스크·산출물·평가는 orch 를 경유한다. 이렇게 하면 상태(목표·현재 버전·백로그)가 한 곳에 모이고, spec/impl 은 언제든 교체·병렬화할 수 있는 무상태 워커가 된다.

목표/버전 흐름 에이전트 메시지 스타 토폴로지 → spec·impl 은 무상태 워커(교체·병렬 가능)
02  Loop Engineering

GOAL_LOOP — 관통테스트로 검증하고 회귀는 백로그로 되먹인다

exec → test → verify → eval 로 한 사이클을 돌린 뒤, 이전 버전보다 좋아졌으면 버전을 올리고, 안좋아졌으면 백로그를 만들어 재계획한다. 핵심은 verify = 사용자 입장 관통테스트(유닛 통과와 별개)라는 점, 그리고 eval 이 회귀를 판정한다는 점이다.

✓ 통과 → 전진 ✗ test 실패(유닛) ✗ verify 실패(관통) ▼ eval 회귀 ▲ 승격

왜 test 와 verify 를 나누나? — userscript 의 self-test(mock 워크시트 회귀검증)는 “파싱 로직이 안 깨졌나”를 본다. 하지만 사용자는 “메뉴가 실제로 먹음직스럽고 원칙을 지키나”를 본다. 전자가 test, 후자가 verify(관통테스트). 둘 다 통과해야 eval 로 넘어간다.

test · verify · eval 실패 시 동작

핵심 구분: 게이트 실패(test/verify) 는 전진 차단 → 재시도·재계획 이고, 회귀(eval) 는 게이트는 통과했지만 이전 버전 대비 하락 → 롤백 이다. 되먹임 목적지가 서로 다르다.

GATEtest
impl 유닛 셀프테스트 실패
(로직이 깨짐 · verify 진입 차단)
  • 즉시 impl 내부 재시도 — 같은 태스크·수용기준
  • 예산 초과 → spec 에 “태스크 재정의” 요청
  • verify/eval 로 넘어가지 않음
한계 재시도 N회 · 버전 승격 후보 아님
GATEverify
유닛은 통과, 사용자 관통테스트 실패
(만들긴 했으나 목표 미충족)
  • orch 가 원인 판별: 구현이 틀렸나 / 기준이 틀렸나
  • 구현 문제 → impl 재실행 (같은 기준)
  • 기준·시나리오 문제 → spec 재계획
한계 재계획 M회→사용자 에스컬레이션 · 버전 승격 안 함
REGeval ▼
게이트는 통과, 이전 버전 대비 점수 하락
(부분 개선이 다른 곳을 악화)
  • 롤백 — 이전 버전을 현행으로 유지
  • 회귀 백로그 생성 (근거·디프 첨부)
  • 백로그 → spec 재계획으로 되먹임
한계 연속 회귀 K회→목표 재검토 · 버전 v 유지(승격 취소)

모든 실패는 근거와 함께 백로그에 기록 → 같은 실패 반복 방지. 모든 재시도·재계획엔 예산이 있고, 소진 시 상위(사용자/목표)로 에스컬레이션 → 무한루프 방지.

03  Role Split

역할분담 — 계획하는 자, 규정하는 자, 만드는 자를 분리한다

모놀리식의 근본 문제는 “무엇을 할지 정하는 판단”과 “실제로 만드는 손”이 같은 컨텍스트에 뒤섞여, 검증이 자기채점이 되고 컨텍스트가 비대해진다는 점이다. 세 역할의 입·출력을 계약(schema)으로 고정한다.

orch 오케스트레이터
STATEFUL · 제어평면

하는 일

  • GOAL_LOOP 상태머신 구동·전이
  • spec/impl 스폰 시점과 라우팅 결정
  • eval(회귀 판정)·버전 승격·롤백
  • 목표·버전 스냅샷·백로그의 유일 보관자
INGOAL, impl 산출물, 백로그
OUT태스크 배정, 버전 승격/롤백
NOT — 도메인 작업(파싱·메뉴구성·코딩)을 직접 하지 않는다. 라우팅과 판정만.
spec 스페시파이어
STATELESS · 태스크 생성

하는 일

  • 목표 → 검증가능한 태스크로 분해
  • 태스크마다 수용기준 부여
  • 관통테스트(verify) 시나리오 작성
  • “완료란 무엇인가”를 소유
IN목표 or 백로그 항목
OUT태스크[] + 수용기준 + 관통테스트
NOT — 구현하지 않는다. 코드/산출물을 만들지 않고 “무엇을·어디까지”만 규정.
impl 임플리멘터
STATELESS · 구현

하는 일

  • 태스크 1건을 받아 산출물 생성
  • 수용기준 충족까지 반복
  • 유닛 셀프테스트를 함께 동봉
  • 작은 단위 → 병렬 fan-out 가능
IN태스크 1건 + 수용기준
OUT산출물 + 셀프테스트 결과
NOT — 목표를 재해석하거나 범위를 넓히지 않는다. 배정된 태스크에만 집중.
04  Build Direction

구축방향 — 가장 작은 검증가능 단위부터 위로 쌓는다

각 단(rung)마다 자체 verify 가 붙는다. 아래 단이 초록이 되어야 위 단을 조립한다. 메뉴 예시(셀 하나 → 한 끼 → 하루 → 주간 → userscript)에 그대로 대응된다.

L1 · 셀
단일 셀 파싱 / 단일 메뉴 항목
F18 한 칸을 이름·설명으로 정확히 분해한다.
verify: mock 셀 → 기대 문자열
L2 · 코너
한 끼 · 한 코너 구성
코너 내 재료 무중복, 밥류 고정 등 국소 원칙.
verify: 코너 내 재료중복 0건
L3 · 하루
하루 단위 식단
코너당 육류 1종/일 등 교차 제약.
verify: 일자 교차 원칙 통과
L4 · 주간
주간 메뉴표 (원본 대비)
9대 원칙 + 원본 무중복 자동검증.
verify: 9대 원칙 전부 ✅
L5 · 시스템
userscript 자동기입 (관통)
xlsx → 보드 파싱 → 미리보기까지 사용자 흐름 전체.
verify: 사용자 관통테스트 통과
05  Better Alternatives

더 나은 대안 — 3-에이전트 기본형을 이렇게 강화한다

요청한 orch/spec/impl 3분할은 좋은 출발점이다. 아래는 “자기채점 편향”과 “회귀 추적” 두 약점을 메우는 보강안이다.

추천

verify 를 impl·spec 에서 떼어 독립 eval 에이전트로 (3→4 분할)

impl 이 자기 코드를, spec 이 자기 기준을 채점하면 편향이 생긴다. 관통테스트를 적대적으로 실행·판정하는 별도 eval(QA) 에이전트를 두면 “정의하는 자(spec)”와 “판정하는 자(eval)”가 분리된다. orch 는 순수 라우팅으로 더 가벼워진다.

WHY  검증 신뢰도 ↑ · 자기채점 제거 — 3-에이전트에서 가장 큰 단일 개선.
A

에이전트 간 계약을 스키마로 고정

spec→impl(태스크), impl→orch(결과)를 userscript 의 PROFILE처럼 엄격한 스키마로 외부화. 워커를 교체·병렬화·재현 가능하게 만든다.

WHY  무상태 워커의 전제조건 · 핸드오프 유실 방지.
B

백로그를 1급 영속 원장으로

회귀를 일회성 메시지가 아니라 우선순위·근거가 붙은 지속 원장에 적재. 되풀이되는 회귀가 “추적되는 부채”가 된다.

WHY  루프가 같은 실수를 반복하지 않게 하는 기억.
C

버전 = 불변 스냅샷 + eval 디프 점수

메뉴 v3→v4 처럼 모든 버전을 보존하고, eval 이 이전 대비 점수 디프를 산출 → 즉시 롤백 가능. “좋아졌나”를 숫자로 만든다.

WHY  회귀 판정의 객관화 · 안전한 되돌림.
D

작은 단위 → impl 병렬 fan-out

구축을 작은 단위로 쪼갠 덕에 L1~L2 태스크는 대체로 독립적. orch 가 impl 여러 개를 동시에 돌리고 결과를 병합.

WHY  “작은 단위부터” 원칙의 자연스러운 성능 배당.
E

eval 은 pass/fail 이 아니라 “사용자 고통 감소”로

관통테스트를 실제 사용자 시나리오(예: 담당자가 xlsx 붙여넣고 미리보기까지)로 정의하고, 통과 여부가 아니라 고통 지표가 내려갔는지로 eval.

WHY  “사용자 입장 관통테스트”의 본래 취지에 정렬.

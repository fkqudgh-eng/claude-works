Hermes · Agent Architecture · rev 0.2

모놀리식 헤르메스를
세 개의 협력 에이전트로 분리한다

지금의 헤르메스는 “판단·계획·구현·검증”을 한 몸으로 처리한다. 이를 분리해 orch 는 목표를 전달하는 work 분배자로 두고, 실무는 각 단계에 배속된 특화 워커가 맡는다. GOAL_LOOP(exec → test → verify → eval)는 언제든 재조립 가능한 단계 컴포넌트이며, 워커는 컴포넌트에 자유 배속되고 사용자는 그 현황·결과를 피드백 받는다.

orch dispatch만 spec 태스크·검증정의 impl 구현·셀프테스트 verify·eval 현재 단일 근거: menu v1→v4 · userscript self-test
01  Relationship Map

시스템 맵 — orch 는 목표를 전달만, 실무는 배속된 워커가 수행한다

orch 는 사용자 목표를 파이프라인에 넘기는 work 분배자다. 실제 작업은 각 단계에 배속된 특화 워커(spec · impl · verify·eval)가 수행하며, 현 단계에서 verify 와 eval 은 한 에이전트가 맡는다. 어떤 워커가 어느 단계에 붙는지는 설정으로 바뀐다(→ §03).

목표 흐름 orch = dispatch만 verify+eval 현재 단일 에이전트 워커 배속은 설정으로 가변 (§03)
02  Loop Engineering

GOAL_LOOP — 관통테스트로 검증하고 회귀는 백로그로 되먹인다

exec → test → verify → eval 로 한 사이클을 돌린 뒤, 이전 버전보다 좋아졌으면 버전을 올리고, 안좋아졌으면 백로그를 만들어 재계획한다. 핵심은 verify = 사용자 입장 관통테스트(유닛 통과와 별개)라는 점. 현 단계에선 verify 와 eval 을 한 에이전트가 담당한다. 이 4단계는 고정이 아니라 언제든 추가·삭제·재배열 가능한 단계 컴포넌트다(→ §03).

✓ 통과 → 전진 ✗ test 실패(유닛) ✗ verify 실패(관통) ▼ eval 회귀 ▲ 승격

왜 test 와 verify 를 나누나? — userscript 의 self-test(mock 워크시트 회귀검증)는 “파싱 로직이 안 깨졌나”를 본다. 하지만 사용자는 “메뉴가 실제로 먹음직스럽고 원칙을 지키나”를 본다. 전자가 test, 후자가 verify(관통테스트). 둘 다 통과해야 eval 로 넘어간다.

test · verify · eval 실패 시 동작

핵심 구분: 게이트 실패(test/verify) 는 전진 차단 → 재시도·재계획 이고, 회귀(eval) 는 게이트는 통과했지만 이전 버전 대비 하락 → 롤백 이다. 되먹임 목적지가 서로 다르다.

GATEtest
impl 유닛 셀프테스트 실패

  • 예산 초과 → spec 에 “태스크 재정의” 요청

모든 실패는 근거와 함께 백로그에 기록 → 같은 실패 반복 방지. 모든 재시도·재계획엔 예산이 있고, 소진 시 상위(사용자/목표)로 에스컬레이션 → 무한루프 방지.

03  Stage Components & Binding

컴포넌트 배속 — 단계는 재조립되고, 특화 에이전트가 자유롭게 붙는다

각 단계는 컴포넌트다. 컴포넌트에는 에이전트를 1개 이상 배속할 수 있고, 다시 하위 컴포넌트로 쪼갤 수 있다. 배속은 설정으로 바뀌며, 사용자는 “어떤 에이전트가 어디에 붙어 무슨 결과를 냈는지” 피드백 받는다.

(spec · 배포 · 문서 …)

① 한 컴포넌트 = 에이전트 1↑ — 부하가 크거나 관점이 다르면 여러 특화 에이전트를 같은 컴포넌트에 병렬 배속.
② 컴포넌트는 하위 컴포넌트로 분할(중첩) — 큰 단계를 잘게 쪼개 배속 단위를 세밀화.
③ 배속은 설정으로 자유 변경 — 코드 수정 없이 어느 에이전트를 어디에 붙일지 재구성.

04  Role Split

역할분담 — 분배하는 자, 규정하는 자, 만드는 자, 검증하는 자

orch 는 목표를 넘기는 work 분배자로 최소화하고, 실무는 단계에 배속되는 특화 워커가 맡는다. 각 워커의 입·출력을 계약(schema)으로 고정해, 컴포넌트에 자유롭게 배속·교체·병렬화할 수 있게 한다. (현 단계 verify·eval 은 한 에이전트.)

05  Build Direction

구축방향 — 가장 작은 검증가능 단위부터 위로 쌓는다

각 단(rung)마다 자체 verify 가 붙는다. 아래 단이 초록이 되어야 위 단을 조립한다. 메뉴 예시(셀 하나 → 한 끼 → 하루 → 주간 → userscript)에 그대로 대응된다.

L1 · 셀

F18 한 칸을 이름·설명으로 정확히 분해한다.

06  Better Alternatives

더 나은 대안 — 현재 구성을 이렇게 강화한다

현 구성(orch 분배 · spec · impl · verify·eval 단일)은 좋은 출발점이다. 아래는 “자기채점 편향”과 “회귀 추적” 두 약점을 메우는 보강안이다.

추천

verify 와 eval 을 분리 — eval 을 독립 판정 에이전트로

현재 verify·eval 은 한 에이전트다. 만드는 자(impl)나 규정하는 자(spec)가 자기 결과를 채점하면 편향이 생기듯, 관통테스트 실행(verify)과 회귀 판정(eval)도 나누면 더 견고하다. §03 배속 모델에서 eval 컴포넌트에 별도 판정 에이전트를 붙이면 코드 변경 없이 4-분할로 확장된다.

WHY  검증 신뢰도 ↑ · 자기채점 제거 — 가장 큰 단일 개선.
A

에이전트 간 계약을 스키마로 고정

spec→impl(태스크), impl→orch(결과)를 userscript 의 PROFILE처럼 엄격한 스키마로 외부화. 워커를 교체·병렬화·재현 가능하게 만든다.

WHY  무상태 워커의 전제조건 · 핸드오프 유실 방지.
B

백로그를 1급 영속 원장으로

회귀를 일회성 메시지가 아니라 우선순위·근거가 붙은 지속 원장에 적재. 되풀이되는 회귀가 “추적되는 부채”가 된다.

WHY  루프가 같은 실수를 반복하지 않게 하는 기억.
C

버전 = 불변 스냅샷 + eval 디프 점수

메뉴 v3→v4 처럼 모든 버전을 보존하고, eval 이 이전 대비 점수 디프를 산출 → 즉시 롤백 가능. “좋아졌나”를 숫자로 만든다.

WHY  회귀 판정의 객관화 · 안전한 되돌림.
D

작은 단위 → impl 병렬 fan-out

구축을 작은 단위로 쪼갠 덕에 L1~L2 태스크는 대체로 독립적. orch 가 impl 여러 개를 동시에 돌리고 결과를 병합.

WHY  “작은 단위부터” 원칙의 자연스러운 성능 배당.
E

eval 은 pass/fail 이 아니라 “사용자 고통 감소”로

관통테스트를 실제 사용자 시나리오(예: 담당자가 xlsx 붙여넣고 미리보기까지)로 정의하고, 통과 여부가 아니라 고통 지표가 내려갔는지로 eval.

WHY  “사용자 입장 관통테스트”의 본래 취지에 정렬.

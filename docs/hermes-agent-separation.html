Hermes · Agent Architecture · rev 0.4

모놀리식 헤르메스를
세 개의 협력 에이전트로 분리한다

지금의 헤르메스는 “판단·계획·구현·검증”을 한 몸으로 처리한다. 이를 분리해 orch 는 목표를 전달하는 work 분배자로 두고, 실무는 각 단계에 배속된 특화 워커가 맡는다. GOAL_LOOP(exec → test → verify → eval)는 언제든 재조립 가능한 단계 컴포넌트이며, 워커는 컴포넌트에 자유 배속되고 사용자는 그 현황·결과를 피드백 받는다.

orch dispatch만 spec 태스크·검증정의 impl 구현·셀프테스트 verify·eval 현재 단일 근거: menu v1→v4 · userscript self-test
01  Relationship Map

시스템 맵 — orch 는 목표를 전달만, 실무는 배속된 워커가 수행한다

orch 는 사용자 목표를 파이프라인에 넘기는 work 분배자다. 실제 작업은 각 단계에 배속된 특화 워커(spec · impl · verify·eval)가 수행하며, 현 단계에서 verify 와 eval 은 한 에이전트가 맡는다. 어떤 워커가 어느 단계에 붙는지는 설정으로 바뀐다(→ §04).

목표 흐름 orch = dispatch만 verify+eval 현재 단일 에이전트 백로그 = loop 내부 아티팩트 (verify·eval 적재 → spec 소비, orch 미경유) 워커 배속은 설정으로 가변 (§04)
02  Loop Engineering

GOAL_LOOP — 관통테스트로 검증하고 회귀는 백로그로 되먹인다

exec → test → verify → eval 로 한 사이클을 돌린 뒤, 이전 버전보다 좋아졌으면 버전을 올리고, 안좋아졌으면 백로그를 만들어 재계획한다. 핵심은 verify = 사용자 입장 관통테스트(유닛 통과와 별개)라는 점. 현 단계에선 verify 와 eval 을 한 에이전트가 담당한다. 이 4단계는 고정이 아니라 언제든 추가·삭제·재배열 가능한 단계 컴포넌트이며, 실행은 중앙 지휘가 아니라 이벤트로 자기전파한다(→ §03·§04).

✓ 통과 → 전진 ✗ test 실패(유닛) ✗ verify 실패(관통) ▼ eval 회귀 ▲ 승격

왜 test 와 verify 를 나누나? — userscript 의 self-test(mock 워크시트 회귀검증)는 “파싱 로직이 안 깨졌나”를 본다. 하지만 사용자는 “메뉴가 실제로 먹음직스럽고 원칙을 지키나”를 본다. 전자가 test, 후자가 verify(관통테스트). 둘 다 통과해야 eval 로 넘어간다.

test · verify · eval 실패 시 동작

핵심 구분: 게이트 실패(test/verify) 는 전진 차단 → 재시도·재계획 이고, 회귀(eval) 는 게이트는 통과했지만 이전 버전 대비 하락 → 롤백 이다. 되먹임 목적지가 서로 다르다.

03  Event Choreography

이벤트 흐름 — 각 단계는 생물처럼 자율로 돌고, 완료는 이벤트가 된다

중앙이 매 스텝을 지휘하지 않는다(코레오그래피). 각 워커는 항상 켜진 자율 루프 — 구독 이벤트 대기 → 작업 → 완료 이벤트 발행. 한 워커의 완료 이벤트가 곧 다른 워커의 task가 되어 시스템이 스스로 전파한다. orch 는 최초 goal.created 하나만 발행한다.

① 대기 구독 이벤트 → ② 작업 각자 독립 수행 → ③ 발행 완료 이벤트 = 다음 워커 task ↺ 발행자는 구독자를 모름 (느슨한 결합)
정방향 이벤트(= 다음 task) 승격 되먹임 → impl 되먹임 → spec 되먹임도 특별 경로가 아니라 그냥 이벤트

예시 체인: goal.created → spec 문서·태스크 작성 완료 spec.done → impl 이 그 태스크 수행 → impl.done → verify·eval 관통·평가 → 통과면 승격, 회귀·기준오류면 spec.replan 으로 돌아가 설계를 변경하거나 잘못된 spec 을 재정리. 각 화살표가 곧 “다른 워커의 새 task”다.

◆ 이벤트 = task — 완료 이벤트가 곧 다음 셀의 작업지시. 별도 지휘자가 필요 없다.
◆ 느슨한 결합 — 발행자는 누가 받는지 모른다. 새 셀(배포·문서 등)은 구독만 등록하면 흐름에 끼어든다(→ §04).
◆ 되먹임도 이벤트 — 실패·회귀도 특별 경로가 아니라 그냥 이벤트라 spec·impl 이 구독해 반응한다. orch 는 관여하지 않는다.
04  Stage Components & Binding

컴포넌트 배속 — 단계는 재조립되고, 특화 에이전트가 자유롭게 붙는다

각 단계는 컴포넌트다. 컴포넌트에는 에이전트를 1개 이상 배속할 수 있고, 다시 하위 컴포넌트로 쪼갤 수 있다. 같은 작업은 하위 컴포넌트로 중첩하거나 독립 단계로 승격해 붙일 수 있다. 배속은 설정으로 바뀌며, 사용자는 “어떤 에이전트가 어디에 붙어 무슨 결과를 냈는지” 피드백 받는다.

07  Better Alternatives

더 나은 대안 — 현재 구성을 이렇게 강화한다

현 구성(orch 분배 · spec · impl · verify·eval 단일)은 좋은 출발점이다. 아래는 “자기채점 편향”과 “회귀 추적” 두 약점을 메우는 보강안이다.

추천

verify 와 eval 을 분리 — eval 을 독립 판정 에이전트로

현재 verify·eval 은 한 에이전트다. 만드는 자(impl)나 규정하는 자(spec)가 자기 결과를 채점하면 편향이 생기듯, 관통테스트 실행(verify)과 회귀 판정(eval)도 나누면 더 견고하다. §04 배속 모델에서 eval 컴포넌트에 별도 판정 에이전트를 붙이면 코드 변경 없이 4-분할로 확장된다.

WHY  검증 신뢰도 ↑ · 자기채점 제거 — 가장 큰 단일 개선.
A

에이전트 간 계약을 스키마로 고정

spec→impl(태스크), impl→orch(결과)를 userscript 의 PROFILE처럼 엄격한 스키마로 외부화. 워커를 교체·병렬화·재현 가능하게 만든다.

WHY  무상태 워커의 전제조건 · 핸드오프 유실 방지.
B

백로그를 1급 영속 원장으로

회귀를 일회성 메시지가 아니라 우선순위·근거가 붙은 지속 원장에 적재. 되풀이되는 회귀가 “추적되는 부채”가 된다.

WHY  루프가 같은 실수를 반복하지 않게 하는 기억.
C

버전 = 불변 스냅샷 + eval 디프 점수

메뉴 v3→v4 처럼 모든 버전을 보존하고, eval 이 이전 대비 점수 디프를 산출 → 즉시 롤백 가능. “좋아졌나”를 숫자로 만든다.

WHY  회귀 판정의 객관화 · 안전한 되돌림.
D

작은 단위 → impl 병렬 fan-out

구축을 작은 단위로 쪼갠 덕에 L1~L2 태스크는 대체로 독립적. orch 가 impl 여러 개를 동시에 돌리고 결과를 병합.

WHY  “작은 단위부터” 원칙의 자연스러운 성능 배당.
E

eval 은 pass/fail 이 아니라 “사용자 고통 감소”로

관통테스트를 실제 사용자 시나리오(예: 담당자가 xlsx 붙여넣고 미리보기까지)로 정의하고, 통과 여부가 아니라 고통 지표가 내려갔는지로 eval.

WHY  “사용자 입장 관통테스트”의 본래 취지에 정렬.
08  Worked Example · 관통 시나리오

한 사이클을 실제 메뉴 사례로 — 이벤트가 스스로 굴러가는 모습

이 저장소의 실제 작업(주간 메뉴 재구성 + self-test userscript)으로 GOAL_LOOP 한 턴을 끝까지 따라간다. 목표 = “주간 메뉴 v5 · 석식 다양성 강화”. 각 단계의 완료가 곧 다음 워커를 깨우는 이벤트다.

1
orch 목표 주입 goal.created
사용자 목표 “v5 · 석식 다양성 강화” 를 파이프라인에 넘긴다. 이후 orch 는 관여하지 않는다.
2
spec 문서작성 → 태스크 배포 task.created ×3
목표를 검증가능 태스크로 분해하고 각 수용기준·관통테스트를 붙여 배포: T1 석식 코너2 5종 재구성(수용: 육류 1종/일 · 원본 무중복) · T2 밋밋한 명칭 개선 · T3 self-test 케이스 갱신.
3
impl 3개 태스크 병렬 수행 impl.done
T1·T2·T3 을 독립적으로(fan-out) 구현하고, 각자 유닛 셀프테스트를 동봉해 산출물 제출.
✓
test 유닛 셀프테스트 통과
self-test(mock 워크시트 → 기대 파싱값) 회귀검증 통과 — “파싱 로직은 안 깨졌다”.
✗
verify·eval 관통 자동검증 실패 verify.failed(구현)
9대 원칙 자동검증에서 “코너 내 재료중복 1건” 적발. 기준이 아니라 구현 미달로 판정 → T1 을 impl 로 되돌린다(같은 수용기준).
6
impl T1 재실행 impl.done
중복 재료를 다른 재료·조리로 교체해 재제출. 되먹임은 특별 경로가 아니라 그냥 이벤트였다.
✓
verify·eval 관통 통과 → 평가 verify.passed
verify: 9대 + 신규 원칙 전부 통과. eval: v4 대비 석식 다양성 지표 ↑, 타 원칙 유지 → 개선으로 판정.
▲
verify·eval 승격 → v5
새 버전 v5 로 승격. 다음 목표를 기다린다. 한 턴 동안 orch 는 1번 이후 아무 것도 하지 않았다.
분기 — 만약 7단계 eval 이 회귀였다면(예: 다양성은 늘었지만 원가 지표가 악화) → eval.regressed 발행 → v4 로 롤백 + 회귀 백로그 적재 → spec 이 구독해 재설계(spec.replan). 승격 대신 이 경로를 탄다.

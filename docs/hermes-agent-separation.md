# 헤르메스 에이전트 분리 설계 (rev 0.4)

> 시각 자료: [`hermes-agent-separation.html`](./hermes-agent-separation.html) — 시스템 맵·GOAL_LOOP·컴포넌트 배속 스키매틱 포함.

지금의 **헤르메스**는 판단·계획·구현·검증을 한 몸으로 처리하는 모놀리식 에이전트다.
(근거: 이 저장소의 `menu/` 재구성 v1→v4 와 self-test 내장 `cloudcast-menu-autofill.user.js`.)

이를 분리해 **orch 는 목표를 전달하는 work 분배자**로 최소화하고, 실무는 각 단계에 **배속된 특화 워커**가 맡는다.
**GOAL_LOOP**(exec → test → verify → eval)는 언제든 **재조립 가능한 단계 컴포넌트**이며, 워커는 컴포넌트에 자유 배속되고 사용자는 그 현황·결과를 피드백 받는다.

---

## 1. 시스템 맵 — orch 는 전달만, 실무는 배속 워커

```
        목표 주입
  GOAL ───────────▶  orch (work 분배 · dispatch only)
                        │  dispatch (단계에 배속 실행)
            ┌───────────┼───────────────────────┐
            ▼           ▼                        ▼
          spec        impl               verify · eval ──▶ 사용자 피드백
       (태스크·검증)   (구현·셀프테스트)   (관통테스트 + 평가, 현재 단일)
            ▲                                    │
            │ 재투입(재계획)                      │ 적재
            └──────────  BACKLOG  ◀──────────────┘
                     (loop 내부 아티팩트 · orch 미경유)
```

- **orch = work 분배자.** 사용자 목표를 파이프라인에 넘기는 것까지가 역할. 판단·구현·평가는 하지 않는다.
- 실무는 각 단계에 배속된 특화 워커(**spec · impl · verify·eval**)가 수행.
- **현 단계에선 verify 와 eval 을 한 에이전트(`verify·eval`)가 담당.**
- **백로그는 orch 를 거치지 않는다.** 한 목표 내부의 loop 상태이므로 `verify·eval` 이 적재하고 `spec` 이 소비(재계획)한다. 재투입 스케줄링을 orch 에 얹으면 “dispatch만” 원칙과 어긋나므로, orch 는 최초 목표만 주입한다.

## 2. GOAL_LOOP — 관통테스트로 검증, 회귀는 백로그로 되먹임

4단계 `exec → test → verify → eval` 은 **고정이 아니라 재조립 가능한 단계 컴포넌트**다(→ §3).

```
  ┌───────────────────────── promote · 다음 목표 (v+1) ◀──────────────── 새 버전 (v+1)
  │                                                                            ▲ 좋아짐
  ▼      ✓          ✓            ✓                                             │
 exec ──▶ test ──▶ verify ──▶ eval ──▶ ◇ 개선?
 (impl)    │ ✗       │ ✗       └─ verify+eval = 현재 한 에이전트 ─┘  │ ▼ 회귀
  ▲        ▼ 유닛실패  ▼ 관통실패                                     ▼
  │    impl 재시도  spec 재계획/impl 재실행                     롤백 + 회귀 백로그
  │        │         │                                              │
  └────────┴─────────┴──────────────────────────────────────────────┘   ← 되먹임 레인
           실패 근거 백로그 기록 · 예산 소진 시 상위 에스컬레이션
```

| 단계 | 소관 | 내용 |
|------|------|------|
| **exec** | impl | 배정된 태스크를 실제로 구현 |
| **test** | impl | 유닛 셀프테스트 — “로직이 안 깨졌나” |
| **verify** | verify·eval | **사용자 입장 관통테스트** — “실제로 원칙을 지키고 먹음직스럽나” |
| **eval** | verify·eval | 이전 버전 대비 **좋아졌나/안좋아졌나** 회귀 판정 (현재 verify 와 같은 에이전트) |

**test 와 verify 를 나누는 이유:** self-test 는 파싱 로직 무결성을, verify(관통테스트)는 사용자 관점 결과 품질을 본다. 둘 다 통과해야 eval 로 넘어간다.

### 2-1. test · verify · eval 실패 시 동작

핵심 구분: **게이트 실패(test/verify)** = 전진 차단 → 재시도·재계획, **회귀(eval)** = 게이트는 통과했으나 이전 버전 대비 하락 → 롤백.

| 실패 지점 | 트리거 | 즉시 동작 | 되먹임 | 한계/예산 | 버전 |
|---|---|---|---|---|---|
| **test** (게이트) | 유닛 셀프테스트 실패 | impl 내부 재시도 — 같은 태스크 | 예산 초과 → spec 에 **태스크 재정의** 요청 | 재시도 N회 · verify 진입 차단 | 승격 후보 아님 |
| **verify** (게이트) | 유닛 통과, 관통테스트 실패 | **구현/기준 중 무엇이 틀렸는지 판별** | 구현 문제 → impl 재실행 / 기준 문제 → spec 재계획 | 재계획 M회 → 사용자 에스컬레이션 | 승격 안 함, 이전 버전 유지 |
| **eval ▼** (회귀) | 게이트 통과, 이전 버전 대비 점수 하락 | **롤백** + 회귀 백로그 생성 | 백로그 → spec 재계획 | 연속 회귀 K회 → 목표 재검토 | v 유지 (승격 취소) |

공통 규칙: 모든 실패는 **근거와 함께 백로그에 기록**(반복 방지), 모든 재시도·재계획엔 **예산**이 있고 소진 시 상위 **에스컬레이션**(무한루프 방지).

## 3. 이벤트 흐름 — 자율 실행(코레오그래피)

중앙이 매 스텝을 지휘하지 않는다. 각 워커는 **생물처럼 항상 켜진 자율 루프**다 — `구독 이벤트 대기 → 작업 → 완료 이벤트 발행`. 한 워커의 **완료 이벤트가 곧 다른 워커의 task**가 되어 시스템이 스스로 전파한다. orch 는 최초 `goal.created` 하나만 발행한다.

```
 orch ▸ goal.created
        │
        ▼
      [spec] ──spec.done(task 생성)──▶ [impl] ──impl.done──▶ [verify·eval] ──verify.passed──▶ 새 버전
        ▲                                 ▲                        │
        │ eval.regressed /                │ verify.failed(구현)     │
        │ verify.failed(기준)             └─────────────────────────┘
        └──────────── spec 재설계 · 잘못된 spec 재정리 ────────────────┘
```

**예시 체인:** `goal.created` → spec 문서·태스크 작성 완료 `spec.done` → impl 이 그 태스크 수행 → `impl.done` → verify·eval 관통·평가 → 통과면 승격, 회귀·기준오류면 `spec.replan` 으로 돌아가 *설계 변경 또는 잘못된 spec 재정리*. 각 화살표가 곧 “다른 워커의 새 task”다.

| 이벤트 | 발행 | 구독 | 뜻 · 다음 작업 |
|---|---|---|---|
| `goal.created` | orch | spec | 새 목표 진입 — spec 이 문서·태스크 작성 시작 |
| `task.created` (spec.done) | spec | impl | 구현할 태스크 배포 — impl 이 집어 실행 |
| `impl.done` | impl | verify·eval | 산출물 준비 — 관통·평가 시작 |
| `verify.passed` | verify·eval | → 승격 | 관통 통과 → 새 버전(v+1) |
| `verify.failed`(구현) | verify·eval | impl | 구현 미달 → impl 재실행 |
| `verify.failed`(기준) · `eval.regressed` | verify·eval | spec | 기준·설계 문제 or 회귀 → spec 재설계·재정리 |

속성:
- **독립·병렬** — 각 셀은 서로를 호출하지 않고 이벤트만 보고 반응 → 동시에 각자 일한다.
- **이벤트 = task** — 완료 이벤트가 곧 다음 셀의 작업지시. 별도 지휘자가 필요 없다.
- **느슨한 결합** — 발행자는 누가 받는지 모른다. 새 셀(배포·문서 등)은 **구독만 등록하면** 흐름에 끼어든다.
- **되먹임도 이벤트** — 실패·회귀도 특별 경로가 아니라 그냥 이벤트라 spec·impl 이 구독해 반응. orch 는 관여하지 않는다.

## 4. 컴포넌트 배속 — 단계 재조립 + 자유 배속

각 단계는 **컴포넌트**다. 컴포넌트에는 에이전트를 **1개 이상** 배속할 수 있고, 다시 **하위 컴포넌트**로 쪼갤 수 있다. 같은 작업은 **하위 컴포넌트로 중첩**하거나 **독립 단계로 승격**해 붙일 수 있다.

```
설정 →  [ spec ] + [ exec ] + [ test ] + [ verify·eval ] + ( ＋ 단계 추가: 배포·문서·리뷰 … )
        재조립 가능 — 단계 추가 / 삭제 / 재배열

 spec 컴포넌트 (하위 컴포넌트 + 배속)          verify·eval 컴포넌트 (현재 단일)
   ▸ 문서작성   ← spec·doc, spec·review (1개 이상)  ▸ 관통테스트 ← qa
   ▸ 태스크 배포 ← spec·dispatch (task.created 발행)  ▸ 회귀 판정 ← qa  (같은 qa 하나)
```

**같은 작업('태스크 배포')을 붙이는 두 방식:**
- (a) **하위 컴포넌트** — `[ spec ▸문서작성 ▸태스크배포 ]` : spec 단계 안에 중첩.
- (b) **독립 단계** — `[ spec ] + [ 태스크배포 ] + [ exec ]` : 같은 일을 하는 peer 단계로 승격해 추가.

원칙:
1. **한 컴포넌트 = 에이전트 1개 이상** — 관점이 다르면 여러 특화 에이전트를 같은 컴포넌트에 병렬 배속.
2. **컴포넌트는 하위 컴포넌트로 분할(중첩)** — 큰 단계를 잘게 쪼개 배속 단위를 세밀화.
3. **중첩 ↔ 독립 단계 자유 선택** — 같은 작업을 하위 컴포넌트로 넣거나 별도 단계로 승격해 붙일 수 있다(a·b).
4. **배속은 설정으로 자유 변경** — 코드 수정 없이 어느 에이전트를 어디에 붙일지 재구성.

**사용자 피드백:** 어느 에이전트가 어느 컴포넌트에 배속됐는지 · 단계별 통과/실패·산출 결과 · 회귀·백로그 알림.

## 5. 역할분담

| | **orch** | **spec** | **impl** | **verify·eval** |
|---|---|---|---|---|
| 성격 | dispatch only · 최소 | Stateless · 태스크 생성 | Stateless · 구현 | Stateless · 현재 단일 |
| 하는 일 | 목표를 파이프라인에 전달, 단계에 워커 dispatch | 목표→태스크 분해, 수용기준·관통테스트 정의 | 태스크 1건 구현 + 셀프테스트 | 관통테스트 실행 + 회귀 판정 + 승격/롤백 |
| IN | GOAL | 목표 or 백로그 항목 | 태스크 1건 + 수용기준 | 산출물 + 관통테스트 시나리오 |
| OUT | 파이프라인에 dispatch | 태스크[] + 수용기준 + 관통테스트 | 산출물 + 셀프테스트 결과 | 통과/회귀 판정 + 결과 피드백 |
| **NOT** | 판단·구현·평가 직접 안 함 | 구현 안 함 | 목표 재해석·범위 확장 안 함 | 구현·태스크 생성 안 함 |

## 6. 구축방향 — 작은 단위 → 큰 단위

각 단마다 자체 verify 가 붙고, 아래 단이 통과해야 위 단을 조립한다.

| 레벨 | 단위 | verify |
|------|------|--------|
| L1 | 단일 셀 파싱 / 단일 메뉴 항목 | mock 셀 → 기대 문자열 |
| L2 | 한 끼·한 코너 구성 | 코너 내 재료중복 0건 |
| L3 | 하루 단위 식단 | 일자 교차 원칙 통과 |
| L4 | 주간 메뉴표(원본 대비) | 9대 원칙 전부 통과 |
| L5 | userscript 자동기입(관통) | 사용자 관통테스트 통과 |

## 7. 더 나은 대안

- **★ 추천 — verify 와 eval 분리 (eval 을 독립 판정 에이전트로).**
  현재 verify·eval 은 한 에이전트다. 만드는 자(impl)·규정하는 자(spec)가 자기 결과를 채점하면 편향이 생기듯, **관통테스트 실행(verify)** 과 **회귀 판정(eval)** 도 나누면 더 견고하다. §4 배속 모델에서 eval 컴포넌트에 **별도 판정 에이전트**를 붙이면 코드 변경 없이 확장된다.
- **A. 에이전트 간 계약을 스키마로 고정** — 핸드오프를 `PROFILE`처럼 외부화 → 교체·병렬·재현 가능.
- **B. 백로그를 1급 영속 원장으로** — 회귀를 우선순위·근거가 붙은 지속 부채로 추적.
- **C. 버전 = 불변 스냅샷 + eval 디프 점수** — 모든 버전 보존, 점수 디프로 즉시 롤백.
- **D. 작은 단위 → impl 병렬 fan-out** — 독립 태스크를 orch 가 동시 dispatch 후 병합.
- **E. eval 을 pass/fail 이 아니라 “사용자 고통 감소”로** — 실제 사용자 시나리오 기준 고통 지표로 판정.

## 8. 관통 시나리오 (worked example)

이 저장소의 실제 작업(주간 메뉴 재구성 + self-test userscript)으로 한 턴을 따라간다. 목표 = **“주간 메뉴 v5 · 석식 다양성 강화”**.

| # | 워커 | 동작 | 발행 이벤트 |
|---|------|------|------------|
| 1 | orch | 목표 주입 (이후 미관여) | `goal.created` |
| 2 | spec | 문서작성 → 태스크 배포 (T1 석식 코너2 재구성 / T2 명칭 개선 / T3 self-test 갱신, 각 수용기준·관통테스트) | `task.created ×3` |
| 3 | impl | T1·T2·T3 병렬 수행 + 셀프테스트 동봉 | `impl.done` |
| 4 | test | mock 워크시트 self-test 회귀검증 통과 ✓ | — |
| 5 | verify·eval | 관통 자동검증서 “코너 내 재료중복 1건” 적발 → 구현 미달 판정 | `verify.failed(구현)` |
| 6 | impl | T1 재실행(중복 재료 교체) | `impl.done` |
| 7 | verify·eval | 9대+신규 원칙 전부 통과, v4 대비 다양성 ↑ → 개선 | `verify.passed` |
| 8 | verify·eval | **v5 승격.** orch 는 1번 이후 아무 것도 안 함 | `→ v5` |

**분기:** 7단계 eval 이 회귀였다면(예: 다양성↑이나 원가 지표 악화) → `eval.regressed` → v4 롤백 + 회귀 백로그 → spec 이 구독해 재설계(`spec.replan`).

### 요약 한 줄
> `orch` 는 최초 목표만 발행하는 work 분배자이고, 실무는 **생물처럼 자율로 도는 워커**(spec·impl·verify·eval)가 **이벤트로 자기전파**하며 수행한다.
> 각 완료 이벤트가 곧 다음 워커의 task이며, `exec→test→verify→eval` 파이프라인은 재조립 가능하고 컴포넌트에 에이전트를 1개 이상(또는 독립 단계로 승격) 붙일 수 있다.
> 사용자는 배속 현황·결과·회귀를 피드백 받는다. — 다음 단계로 `verify` 와 `eval` 을 분리하는 것을 권장.

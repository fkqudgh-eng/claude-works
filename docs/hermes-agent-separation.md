# 헤르메스 에이전트 분리 설계 (rev 0.1)

> 시각 자료: [`hermes-agent-separation.html`](./hermes-agent-separation.html) — 관계도·GOAL_LOOP 스키매틱 포함.

지금의 **헤르메스**는 판단·계획·구현·검증을 한 몸으로 처리하는 모놀리식 에이전트다.
(근거: 이 저장소의 `menu/` 재구성 v1→v4 와 self-test 내장 `cloudcast-menu-autofill.user.js` 를 한 컨텍스트에서 만들어 냄.)
이를 **orch / spec / impl** 세 역할로 분리하고, 그 위에 **GOAL_LOOP** 자기개선 루프를 얹는다.

---

## 1. 에이전트 관계도 (스타 토폴로지)

```
        목표 주입                            ⑤ 회귀 적재 / ⑥ 재투입
  GOAL ───────────▶  ┌───────────────┐  ◀───────────────▶  BACKLOG
                     │     orch       │                     (회귀·부채 원장)
                     │  제어평면·상태  │
                     └──┬─────────┬───┘
        ① 목표→태스크     │         │   ③ 태스크 1건 배정
        ② 태스크+검증기준 ▼         ▼   ④ 산출물+셀프테스트
                    ┌────────┐   ┌────────┐
                    │  spec  │   │  impl  │
                    └────────┘   └────────┘
```

- **orch 가 유일한 라우터.** spec ↔ impl 직접 통신 없음. 모든 태스크·산출물·평가는 orch 경유.
- 상태(목표·현재 버전·백로그)가 orch 한 곳에 모인다 → **spec/impl 은 무상태 워커**(교체·병렬 가능).

---

## 2. GOAL_LOOP (loop engineering)

```
  ┌──────────────────────────────────────── promote (다음 목표) ◀───────────┐
  │                                                                          │
  ▼                                                                    좋아짐 ▲
 exec ──▶ test ──▶ verify ──▶ eval ──▶ ◇ 개선되었나? ──── 새 버전 (v+1)
 (impl)  (유닛    (사용자    (이전                │
        셀프테스트) 관통테스트) 버전대비)         안좋아짐 ▼
  ▲                                          백로그 생성
  │                                              │
  └──────────── spec 재계획 후 재실행 ◀───────────┘
```

| 단계 | 소관 | 내용 |
|------|------|------|
| **exec** | impl | 배정된 태스크를 실제로 구현 |
| **test** | impl | 유닛 셀프테스트 — “로직이 안 깨졌나” (userscript `self-test` = mock 워크시트 회귀검증) |
| **verify** | spec 정의 / (실행) | **사용자 입장 관통테스트** — “실제로 원칙을 지키고 먹음직스럽나” |
| **eval** | orch | 이전 버전 대비 **좋아졌나/안좋아졌나** 회귀 판정 |
| 분기 ▲ | orch | 좋아짐 → **새 버전 승격**, 다음 목표로 되돌림 |
| 분기 ▼ | orch | 안좋아짐 → **백로그 생성**, spec 재계획 후 재실행 |

**test 와 verify 를 나누는 이유:** self-test 는 파싱 로직 무결성을 보고, verify(관통테스트)는 사용자 관점의 결과 품질을 본다. 둘 다 통과해야 eval 로 넘어간다.

## 3. 역할분담

| | **orch** | **spec** | **impl** |
|---|---|---|---|
| 성격 | Stateful · 제어평면 | Stateless · 태스크 생성 | Stateless · 구현 |
| 하는 일 | 루프 구동, 라우팅, eval, 버전 승격/롤백, 상태 보관 | 목표→검증가능 태스크 분해, 수용기준·관통테스트 정의 | 태스크 1건 구현 + 유닛 셀프테스트 동봉 |
| IN | GOAL, impl 산출물, 백로그 | 목표 or 백로그 항목 | 태스크 1건 + 수용기준 |
| OUT | 태스크 배정, 버전 승격/롤백 | 태스크[] + 수용기준 + 관통테스트 | 산출물 + 셀프테스트 결과 |
| **NOT** | 도메인 작업을 직접 안 함 | 구현 안 함 (무엇을·어디까지만) | 목표 재해석·범위 확장 안 함 |

핵심 원칙: **판단(spec) · 실행(impl) · 조율/판정(orch) 을 서로 다른 컨텍스트로 격리** → 검증이 자기채점이 되지 않고 컨텍스트 비대화 방지.

---

## 4. 구축방향 — 작은 단위 → 큰 단위

각 단마다 자체 verify 가 붙고, 아래 단이 통과해야 위 단을 조립한다.

| 레벨 | 단위 | verify |
|------|------|--------|
| L1 | 단일 셀 파싱 / 단일 메뉴 항목 | mock 셀 → 기대 문자열 |
| L2 | 한 끼·한 코너 구성 | 코너 내 재료중복 0건 |
| L3 | 하루 단위 식단 | 일자 교차 원칙 통과 |
| L4 | 주간 메뉴표(원본 대비) | 9대 원칙 전부 통과 |
| L5 | userscript 자동기입(관통) | 사용자 관통테스트 통과 |

메뉴 예시(셀 → 끼 → 하루 → 주간 → userscript)에 그대로 대응.

---

## 5. 더 나은 대안

- **★ 추천 — verify 를 독립 `eval` 에이전트로 (3→4 분할).**
  impl 이 자기 코드를, spec 이 자기 기준을 채점하면 편향. 관통테스트를 **적대적으로 실행·판정하는 별도 QA 에이전트**를 두면 “정의하는 자(spec)”와 “판정하는 자(eval)”가 분리된다. 가장 큰 단일 개선.
- **A. 에이전트 간 계약을 스키마로 고정** — spec→impl, impl→orch 핸드오프를 `PROFILE`처럼 외부화 → 교체·병렬·재현 가능.
- **B. 백로그를 1급 영속 원장으로** — 회귀를 우선순위·근거가 붙은 지속 부채로 추적, 같은 실수 반복 방지.
- **C. 버전 = 불변 스냅샷 + eval 디프 점수** — 모든 버전 보존, 점수 디프로 즉시 롤백. “좋아졌나”를 숫자화.
- **D. 작은 단위 → impl 병렬 fan-out** — L1~L2 독립 태스크를 orch 가 동시 실행 후 병합.
- **E. eval 을 pass/fail 이 아니라 “사용자 고통 감소”로** — 실제 사용자 시나리오 기준 고통 지표로 판정 → “사용자 입장 관통테스트” 취지에 정렬.

### 요약 한 줄
> `orch`(조율) 가 `spec`(무엇을) 과 `impl`(어떻게) 을 스타 토폴로지로 지휘하고,
> `exec→test→verify→eval` 루프로 매 버전을 사용자 관통테스트로 검증하며,
> 회귀는 백로그로 되먹이고, 작은 단위부터 위로 쌓는다. — 여력이 되면 `verify` 를 독립 `eval` 에이전트로 떼는 4-분할을 권장.
